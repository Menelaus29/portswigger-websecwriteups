## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). The functionality uses the session cookie to identify the user who has made the requests, and its parameters is trivially predictable. We can therefore construct some HTML and deliver it to the user who is logged in, resulting in them changing their email to our arbitrary value.
## Reconnaissance

- After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
- The request to changing our email address is `POST /my-account/change-email`, with, still, the existence of the `Cookie` header and the parameter `email`, with the value being the email address we are changing to.
We have all the conditions necessary to confirm and perform a CSRF attack.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="aaa&#64;gmail&#46;com" /> <!-- the email address to change your victim's email address to !-->
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app relies on the `Cookie` header as the sole mechanism to handle sessions and identify users. There is no other mechanism in place to validate user requests or track sessions. The server also uses `SameSite=None` in its `Set-Cookie` header and the cookie has the `Secure` flag, the `Cookie` (which is also used as the sole session handling mechanism) is appended into our request. Additionally, there is no `CSRF` token to serve as an unpredictable component in the request.
## Remediation

- Include a CSRF token. It should be cryptographically strong, unpredictable, and unique for each user session. This token must be included as a hidden field in all state-changing HTML forms (POST, PUT, DELETE). The server must validate that the token in the incoming request matches the token tied to the user's session before processing the action.
- Set the `SameSite` attribute on the session cookie to `Lax` or `Strict`.
    - `SameSite=Lax` (Default in modern browsers): Prevents the cookie from being sent in cross-site POST requests, mitigating this specific form-based CSRF attack.
    - `SameSite=Strict`: Prevents the cookie from being sent in _any_ cross-site request.
- For high-impact state changes (e.g., email updates, password resets, account deletion), require the user to re-enter their current password or provide secondary authentication (MFA).
