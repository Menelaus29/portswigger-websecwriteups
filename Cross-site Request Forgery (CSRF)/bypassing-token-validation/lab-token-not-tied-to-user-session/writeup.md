## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). Though it uses anti-CSRF token to try to prevent CSRF attacks, these tokens aren't tied to user session, meaning an attacker can use their own legitimate, unexpired `CSRF` token to perform state-changing actions on any arbitrary account.
## Reconnaissance

After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
- Per the lab's description, "they (the CSRF tokens) aren't integrated into the site's session handling system." This means the app does not check if the CSRF token belongs to the same user performing requests.
- I tried intercepting the request to changing `wiener`'s account email (`POST /my-account/change-email`), then let it pass through (means actually changing `wiener`'s account email). After that, I logged out, logged into `carlos`'s account, intercepted the request to changing `carlos`'s account email, sent that request to repeater then **dropped** the request (means `carlos`'s account email wasn't changed). Then, I changed the `CSRF` token (in the `csrf` parameter) from `carlos`'s to `wiener`'s (from the email changing request we let passed through earlier), sent the request. It resulted in a `400 Bad Request` HTTP Response that read `"Invalid CSRF token"`. 
- I tried repeating the whole process again, with the only difference being that I **dropped** the request to change `wiener`'s account email earlier (means `wiener`'s account email remained unchanged). This time, it worked, as we were able to use `wiener`'s CSRF token to change `carlos`'s account email.
The failure before is presumably because when we let that request pass through, the CSRF token is expired and no longer placed in the valid pool of CSRF tokens.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="aaaaa&#64;gmail&#46;com" />
      <input type="hidden" name="csrf" value="token-value" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint. The valid, unexpired CSRF token that we obtained from the request of a state-changing action is also injected as the input, and since the site does not check if this CSRF token really belongs to the same user making the request, it successfully bypassed the anti-CSRF mechanism. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app relies on the `Cookie` header as the sole mechanism to handle sessions and identify users. There is no other mechanism in place to validate user requests or track sessions. Additionally, the app also doesn't check if the CSRF token of a state-changing request belongs to same user performing the request.
## Remediation

- When a user authenticates, the server should generate a cryptographically strong, unpredictable CSRF token and store it securely within the user's server-side session object.
- During any state-changing request (POST, PUT, DELETE), the application must verify that the CSRF token submitted in the request body or headers matches the token stored in the active user's session.
- Tokens should be regenerated upon privilege level changes (e.g., login/logout) to prevent session fixation and token reuse.
- Set the `SameSite` attribute on the session cookie to `Lax` or `Strict`.
    - `SameSite=Lax` (Default in modern browsers): Prevents the cookie from being sent in cross-site POST requests, mitigating this specific form-based CSRF attack.
    - `SameSite=Strict`: Prevents the cookie from being sent in _any_ cross-site request.
