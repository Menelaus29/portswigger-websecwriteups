## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). It attempts to block CSRF attack with the inclusion of the CSRF token, but only do so when the request method is `POST`, not with `GET`, even when you can perform state-changing actions with `GET`. This allows us to host an HTML page that uses a CSRF attack with the method `GET` to change the victim's email address.
## Reconnaissance

- After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
- The request to changing our email address is, by default, `POST /my-account/change-email`, with, still, the existence of the `Cookie` header and the parameter `email`, with the value being the email address we are changing to. There is a CSRF token that appears to be legitimate (in terms of strength).
- However, when we change the request method of this request to `GET`, the request line becomes: `GET /my-account/change-email?email=a%40gmail.com&csrf=random-value`. Try omitting the `csrf` token from the request line and sending `GET /my-account/change-email?email=a%40gmail.com`, we get a `302 Found` HTTP Request signifying a redirection, that, when followed, shows that we have successfully change our email address without the CSRF token.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email">
      <input type="hidden" name="email" value="aaa&#64;gmail&#46;com" />
      <input type="submit" value="Submit request" /> 
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint, using the `GET` request method (omitted from the `<form` element, so by default it is a `GET` request). The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app relies on the `Cookie` header as the sole mechanism to handle sessions and identify users. There is no other mechanism in place to validate user requests or track sessions. The server also uses `SameSite=None` in its `Set-Cookie` header and the cookie has the `Secure` flag, the `Cookie` (which is also used as the sole session handling mechanism) is appended into our request. Additionally, although there is an attempt to include and validate a legitimate `CSRF` token to serve as an unpredictable component in the request, this only applies to `POST` requests, which is insecure since `GET` requests can also be used to perform state-changing actions.
## Remediation

- Include a CSRF token. It should be cryptographically strong, unpredictable, and unique for each user session. This token must be included as a hidden field in all state-changing HTML forms (POST, PUT, DELETE). The server must validate that the token in the incoming request matches the token tied to the user's session before processing the action.
- The server should be configured to reject state-changing actions via `GET`. It is meant to be safe, idempotent, used only for read-only operations and never alter state.
- Set the `SameSite` attribute on the session cookie to `Lax` or `Strict`.
    - `SameSite=Lax` (Default in modern browsers): Prevents the cookie from being sent in cross-site POST requests, mitigating this specific form-based CSRF attack.
    - `SameSite=Strict`: Prevents the cookie from being sent in _any_ cross-site request.
- For high-impact state changes (e.g., email updates, password resets, account deletion), require the user to re-enter their current password or provide secondary authentication (MFA).
