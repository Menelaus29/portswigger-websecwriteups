## Vulnerability Summary

The app's change email functionality is vulnerable to Cross-site Request Forgery (CSRF). There is no anti-CSRF token implemented in state-changing actions. Though the app does attempt to mitigate CSRF with `SameSite=Lax` enabled by default, we can bypass this by using the `_method` parameter.
## Reconnaissance

- After logging in with the provided credentials `wiener - peter`, intercept the request to changing the account's email (`POST /my-account/change-email`). The app doesn't show any explicit `SameSite` restrictions when setting session cookies, but I use Firefox, which as of August 2026 does **not** use `SameSite=Lax` by default, but other mechanisms to prevent cross-site tracking. Therefore, I tried generating a HTML webpage as a CSRF PoC using this `POST` request and delivered it to victim in the exploit server. That did not work.
- I tried changing the request method of `POST /my-account/change-email` to `GET /my-account/change-email?email=b%40gmail.com`. This resulted in a `405 Method Not Allowed` HTTP Response with the header `Allow: POST`.
- Same `GET` request, but with `&_method=POST` appended in the request line, got accepted by the server (`302 Found` that redirects to a successful account's email change). We have successfully bypassed the anti-CSRF mechanisms.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <input type="hidden" name="&#95;method" value="POST" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint, using the `GET` request method (omitted from the `<form` element, so by default it *appears* to be a `GET` request). This helps us bypass the app's anti-CSRF mechanisms. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app lacks a CSRF token. It relies only on the `SameSite` setting and the `POST` method restriction to defend against CSRF, which can be bypassed as shown above.
## Remediation

- Do not rely solely on `SameSite` cookie attributes or HTTP method restrictions. Implement the Synchronizer Token Pattern for all state-changing actions. Rule of thumb: GET requests that only read data do not need a CSRF token, but POST/PUT/DELETE requests that performs state-changing actions almost always need one. Also, the server should be configured to reject state-changing actions via `GET`. It is meant to be safe, idempotent, used only for read-only operations and never alter state.
- Framework-level method overrides (like `_method`) should be disabled globally unless strictly required by legacy clients.
- If method overrides must be permitted, ensure that the application's CSRF middleware evaluates the _resolved_ HTTP method (POST) rather than the _original_ request method (GET), ensuring tokens are still mandated.
