## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). There is no anti-CSRF token implemented in state-changing actions. Though the app does attempt to defend against CSRF attacks with the use of `SameSite=Strict`, we can exploit an unsanitized, user-supplied endpoint to trigger a client-side redirection and perform a state-changing action (changing the victim's account email) with a `GET` request.
## Reconnaissance

- Logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`, we see that in the response to the login request (`POST /login`) has `SameSite=Strict` when setting session cookies. This prevents the browser from including the cookies in cross-site requests, which means that if we want to exploit CSRF, our request has to be treated as same-site.
- Intercept the request to changing our account `wiener`'s email (`POST /my-account/change-email`). Notice that when changing the request method to `GET` (`GET /my-account/change-email?email=a%40gmail.com&submit=1`), it works too. There is also no anti-CSRF token implemented.
- Click on a random post and submit a comment. The request of the comment submission is `GET /post/comment/confirmation?postId=1`. I notice that after a time, the site automatically redirects us to the post that we commented on (`postId=1`).
- Further inspecting the above mechanism lead us to a `commentConfirmationRedirect.js` script that handles this redirection process. The exact content of this script reads:
```js
redirectOnConfirmation = (blogPath) => {
    setTimeout(() => {
        const url = new URL(window.location);
        const postId = url.searchParams.get("postId");
        window.location = blogPath + '/' + postId;
    }, 3000);
}
```
- After 3 seconds, the site automatically redirects us to the post we commented on. What's interesting is that there appears to be no validation mechanism regarding the value of the `postId` parameter. This is confirmed by supplementing the parameter with a random value (`/post/comment/confirmation?postId=aaa`). The confirmation page attempts to redirect us to  a path containing our injected string (`/post/aaa`). This is going to be our vector to exploit CSRF, as a client-side redirection like this is **not** considered cross-site, thus has the ability to bypass the cookie setting `SameSite=Strict`.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/post/comment/confirmation">
      <input type="hidden" name="postId" value="&#46;&#46;&#47;my&#45;account&#47;change&#45;email&#63;email&#61;b&#64;gmail&#46;com&amp;submit&#61;1" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint, using the `GET` request method (omitted from the `<form` element, so by default it is a `GET` request). The input field is hidden to make the page appears as normal, the injected value of the `postId` parameter is, HTML entity encoded, `../my-account/change-email?email=b%40gmail.com%26submit=1`, which uses a path traversal sequence to go from `/post` to root directory (`/`), then to the account's email changing path. Note that the ampersand (`&`) must be URL-encoded to `%26`, else it would be treated as a distinct parameter for the `post/comment/confirmation` endpoint rather than part of the path. `<input type="submit" value="Submit request" />` is for if the victim's browser has JavaScript disabled (not applicable in this case). Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 

## Root Cause

The user-modifiable `postId` parameter is unsanitized, allowing us to inject a path traversal sequence (`../`) to escape the intended path and then the path to changing an user's account email.
## Remediation

 - Include a CSRF token. It should be cryptographically strong, unpredictable, and unique for each user session. This token must be included as a hidden field in all state-changing HTML forms (POST, PUT, DELETE). The server must validate that the token in the incoming request matches the token tied to the user's session before processing the action.
- The server should be configured to reject state-changing actions via `GET`. It is meant to be safe, idempotent, used only for read-only operations and never alter state.
- Keep the redirect path (determined by the `postId` parameter) hidden and strictly server-side. If it has to be exposed in the request, sanitize and validate the parameter using a whitelist, e.g., strictly input must be strictly numeric. Reject/recursively strip path traversal sequences before sending the request to the server for processing.
